# PR 51: 优化状态更新与清理历史消息哨兵

## PR摘要
优化 WuKongIM 状态更新（status update）发送方式，将其改为异步非阻塞模式；同时在编排器（Orchestrator）中过滤历史发送队列，剔除异常消息（LLM失败，任务失败等），防范其作为上下文影响大模型生成逻辑（防范历史中毒）。

## 背景
1. **状态更新同步阻塞卡顿**：
   在 `WuKongIMChannel` 中，`send_status_update` 在之前会使用同步 `.await` 等待服务器返回 JSON-RPC 响应。由于状态更新是高频且尽力而为（Best-effort）的进度信号，当 WuKongIM 服务器响应变慢或 socket 连接处于半关闭状态时，同步等待往返响应会严重卡顿/阻塞 Agent 的主工作线程，导致会话处理延迟。
2. **异常消息影响大模型上下文**：
   当任务超时、失败或会话中断时，系统会向历史会话记录中注入特定的异常消息/哨兵指示文本（如 `[Task failed — not continuing this request]`）。在后续的对话交互中，如果这些异常消息积压在大模型的上下文历史中，LLM 会误学习该回复模式，开始盲目复读这类异常错误提示，从而严重影响大模型的正常生成。

## 方案
1. **异步非阻塞发送（Status Update）**：
   重构 `WuKongIMChannel::send_status_update`，克隆当前通道实例并将其包裹在 `tokio::spawn` 异步任务中执行。主执行路径不再同步等待 `send_status_message_with_topic` 的 RPC 往返，实现高频进度卡片更新的异步非阻塞投递。如果在发送中产生任何 RPC 级错误，仅记录 `tracing::debug` 日志，避免错误向上抛出。
2. **就地过滤异常消息**：
   在 `zeroclaw-channels` 编排器（Orchestrator）的消息处理流 `process_channel_message` 里加入专门的历史清理块。匹配并移除 `prior_turns` 历史消息中所有内容匹配 `SENTINELS` 常量（即LLM失败、任务超时、系统中断等异常消息）的 assistant 轮次，同时移除导致该异常的上一条对应的 user 轮次，以此保持历史消息的用户-助手交替顺序，防止异常消息影响大模型上下文。

## 实现要点
- 通过 `tokio::spawn` 实现了 WuKongIM 通道的非阻塞状态消息上报。
- 编排器里对 `prior_turns` 执行向后遍历并删除，采用 `saturating_sub` 算法防止索引越界和下溢。

## 测试方案
1. **高频发送与延迟容忍性验证**：
   模拟 WuKongIM 服务端极端高延迟响应，触发高频 status 更新，确保客户端主执行路径无任何挂起与变慢现象。
2. **历史中毒防御验证**：
   故意引发任务超时和失败，确保对应的哨兵消息正确写入存储。之后发起新的正常提问，验证 Orchestrator 在将历史传给 LLM 之前是否已剔除哨兵，并检查 LLM 回答是否表现正常（无哨兵文本复读）。
3. **回归测试**：
   运行 `cargo test` 确保未引入任何逻辑断言破坏。
