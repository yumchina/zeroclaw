# PR 52: 重构出站消息为异步非阻塞模式与收紧心跳超时

## PR摘要
重构 WuKongIM 客户端的所有出站数据包发送逻辑，将其由同步 RPC 等待模式彻底改造为异步非阻塞模式；同时收紧心跳超时检测判定与活跃度更新逻辑，**核心修复 macOS 休眠后重新打开电脑时，小助手没有响应（本地 WebSocket 链接看似存在，但由于心跳无法正常收发，WuKongIM 服务端实际已判定小助手离线）的假死问题**，并将心跳超时检测阈值从 90s 下调至 60s。

## 背景
1. **macOS 休眠唤醒后的小助手假死失联**：
   在 macOS 系统休眠并重新唤醒后，客户端的 WebSocket 连接在表面上可能依然显示存活，但实际上连接早已因休眠中断或协议栈挂死，导致心跳包无法正常发出与接收。此时从 WuKongIM 服务端侧来看，小助手已经离线，无法推送消息；而客户端因没有触发重连逻辑而无任何响应，处于长期的假死失联状态。
2. **同步出站 RPC 造成网络吞吐瓶颈**：
   原先在 `WuKongIMChannel` 中，普通消息发送、应用命令、文件消息发送以及审批通道（Approval Channel）交互都会同步调用 `self.send_rpc("send", params).await`，这会迫使客户端同步等待 WuKongIM 服务端返回 JSON-RPC 成功应答。由于网络不稳定或服务器短时高载，此同步屏障会频繁引起发送阻塞和多余的超时判断。
3. **底层 TCP/WS 活动掩盖应用层业务中断**：
   原有 WebSocket 消息循环中，只要从通道读取到任何帧（包括 raw WS 层的 Ping/Pong 控制帧或心跳），便会更新 `last_activity`。然而，在实际生产中，即便底层的 TCP/WS 层握手与控制包在交互，应用层服务端也有可能已经卡死无法处理业务文本数据。这种不加区分的活跃度更新容易产生假死连接。
4. **心跳检测判定时长过长**：
   `HEARTBEAT_TIMEOUT` 在之前设定为 90 秒，对于快速发现并恢复断网连接而言过长。

## 方案
1. **彻底改为异步非阻塞模式**：
   提取出 `send_params_fire_and_forget`（出站异步非阻塞发送函数）辅助函数。该函数在打包序列化 JSON-RPC 的 `send` 方法请求帧后，直接通过底层的 `send_ws_frame` 发送，不挂载任何等待响应的回调。将原先的 `self.send_rpc("send", ...)` 替换为 `send_params_fire_and_forget`，提高网络写出吞吐。
2. **精细化活跃度检测**：
   在 WebSocket 消息循环中，将 `last_activity = Instant::now();` 的更新移入对帧类型解包为 `WsMsg::Text` 的条件分支内。只有真正收到应用层业务 Text 文本消息时，才视为客户端处于活跃状态，剔除 connection 级别的 ping/pong 干扰。
3. **下调心跳超时时间**：
   将 `HEARTBEAT_TIMEOUT` 从 90 秒下调至 60 秒。

## 配置（Optional)
- 心跳超时常量 `HEARTBEAT_TIMEOUT` 修改为 `Duration::from_secs(60)`。

## 实现要点
- `send_params_fire_and_forget`（出站异步非阻塞发送函数）的实现与应用。
- 精准控制 `last_activity` 的更新条件（必须为解包成功的 `WsMsg::Text` 帧）。
- 移除了裸 WS 层的 `WsMsg::Ping` 发送，完全由应用层 JSON-RPC 心跳维持。
